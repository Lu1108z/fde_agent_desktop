# FDE 产设大师｜产品体验分析报告

**评估日期：2026-11-02 · 源码版本：3.3.12 · 评估视角：FDE 项目经理 / 初次使用者 / 产品体验官**

## 一、核心结论

**产品已经具备“带着项目经理完成产品设计”的明确方向，下一阶段最值得投入的是：让任务入口更聚焦、流程状态更可信、失败后更容易恢复。**

五阶段框架、交付物模板、客户事实与 AI 推断的区分、版本归档和人工核对，构成了比较有价值的业务基础。但实际体验中，“流程讲得清楚”和“系统真的按流程正确推进”之间仍有落差。

最值得优先处理的三件事：

1. **修正项目创建与异常处理。** 不同中文项目名包含相同英文词时，可能指向同一个旧项目；创建中途失败还可能留下无法正常重试的目录。
2. **统一完成状态与推进条件。** 阶段一未完成时会出现“五个步骤都已完成”的提示；界面称目标必填，但交接操作实际只检查负责人。
3. **让首页和项目空间始终回答“我现在该做什么”。** 当前首页更擅长展示方法论，项目内部又同时出现阶段导航、步骤导航和交付物导航，使用者需要自行理解它们的关系。

### 四个维度的判断

| 维度 | 当前判断 | 优先改进点 |
|---|---|---|
| 使用体验 | 核心操作已经有引导，入口与术语仍偏多 | 减少找入口、重复填写和异常后的猜测 |
| BUG 与可靠性 | 已发现影响创建、状态可信度和恢复的实际问题 | 先修创建身份、失败反馈、完成判定 |
| 视觉观感 | 蓝白品牌统一、干净，部分页面偏“轻”和“展示型” | 增强正文对比度，压缩装饰和重复导航 |
| 流程化 | 前三阶段已形成任务化骨架，产品核对与技术验收有区分 | 让待办、文档、阶段、交接使用一致的状态依据 |

这里使用定性判断，不把主观观察包装成经过用户统计的评分。

## 二、评估范围与证据

### 本次实际做了什么

- 浏览了工作台、新建项目、阶段说明、技能中心、知识中心、教练、设置和初始化页面。
- 在 **1440×1000、1280×800** 视口检查主要布局。

- 执行现有三个逻辑测试文件，共 **27 项，25 项通过、2 项失败**，详情见第九节。

### 证据的适用范围

- **页面实测**：浏览器渲染与实际前端交互；项目、授权和引擎就绪信息来自隔离样例。
- **逻辑复现**：执行实际业务函数，文件写入临时目录。
- **代码风险**：从实现确认触发条件，但尚未做完整桌面端端到端复现。
- **体验建议**：基于页面与任务分析提出的设计判断。

当前浏览器没有 Electron IPC。浏览器预览中的“项目服务未连接”、模型不可用，以及初始化环境无法检查，**不能直接证明桌面产品发生了对应故障**。真实模型生成质量、语音效果、飞书/极库云登录、安装授权全过程和导出排版不在本次完成验证的范围内。

评估针对当前工作区，其中包含尚未提交的开发内容，并非对已发布安装包的完整验收。页面原始观察记录见 [observations.json](observations.json)。

## 三、值得保留的产品优势

### 1. 业务过程比普通 AI 对话工具更明确

五阶段明确说明了调研、需求沟通、确认、实施和试用的关系。阶段二限定为对接确认表、AI 能力清单和原型，PRD 放到阶段三，这个安排有助于避免过早写大量文档。

### 2. AI 能力围绕业务成果组织

任务按钮已经采用“整理本轮需求”“生成演示原型”等业务语言；资料、模板与输出文件之间存在关联。技能详情里的“你提供 / 你得到”也比直接展示提示词更容易理解。

### 3. 已考虑 AI 结果的可信度

阶段一区分资料事实、行业推测和待确认信息；阶段二、三保留人工核对、确认人和依据。这是面向真实客户项目的重要基础。

### 4. 已有恢复与复核意识

流程实现包含成果归档、版本指纹、修改后的重新核对、生成中断后的恢复，以及研发接收与技术验证分别登记。应继续把这些能力转化为统一、可见的用户体验。

### 5. 整体品牌观感有辨识度

蓝白底色、分阶段图标、卡片圆角及教练形象形成了统一印象。当前更适合在现有视觉基础上提高可读性和效率。

## 四、使用体验：用户卡在哪里

### 4.1 首页：方法论清楚，“下一步”还不够具体

**观察**：首页提供进行中项目、五阶段流程、常用资源、实施基线和待办。已有项目时，“继续处理”是明确入口；但待办主要由文件是否存在推导，常出现“生成某文档”或“核对某阶段交付物”这样的泛任务。

**影响**：用户知道自己在阶段二，却不一定知道现在要补客户纪要、修改哪条需求，还是等待客户确认。

**建议**：

- 项目卡直接展示：**当前任务、缺少的输入、主要阻塞、上次操作、继续按钮**。
- 待办由工作流当前任务和问题状态生成。例如“补充门诊量异常阈值的确认依据”，比“核对需求沟通交付物”更有用。
- 将阶段学习入口命名为“阶段指南”，项目执行入口命名为“继续任务”。
- 实施基线可按当前阶段展示；前三阶段默认优先呈现需求与交付事项。
- 保留五阶段概览，但避免与项目进度重复占据过多首屏面积。

证据：[带项目的首页](home-fixture.png)。

### 4.2 导航：项目概念存在两套落点

**观察**：顶栏“项目”默认进入飞书项目进度；本地工作成果位于“项目与交付物”。资源下又包含团队资料库、代码仓、知识中心和技能中心。

**影响**：新用户可能先进入需要登录的外部页面，仍不知道如何在本地开始工作；也容易混淆项目资料、团队资料与模板。

**建议**：

- 默认“项目”进入本地项目列表，将“团队进度 · 飞书”保留为清楚标注的次级入口。
- 项目空间统一使用“当前任务 / 项目资料 / 交付成果 / 项目概览”。
- 将资料用途解释清楚：项目资料是输入，交付成果是输出，知识模板是方法参考，团队资料是共享来源。
- 顶部子菜单增加明确的展开标识；点击、悬停和键盘聚焦的结果要可预期。

### 4.3 新建项目：输入门槛低，但控制感不足

**观察**：创建页只有需求输入框，名称取前 20 个字符；文案默认“医院背景”；快捷键只提示 Ctrl+Enter。

**建议**：

- 增加可编辑的“项目名称”，需求描述作为独立字段。
- 名称可以自动建议，但不要让截断后的需求承担项目身份。
- 明确创建后会进入“阶段一：明确目标”，保留刚刚输入的需求。
- 若产品定位跨行业，默认写“客户背景”，医疗作为示例；若专注医疗，统一首页、宣传和示例的定位。
- Mac 使用 ⌘+Enter，并在错误发生时保留输入、显示原因和重试入口。

### 4.4 项目工作区：方向正确，导航层级偏重

**观察**：项目侧栏约 248px，阶段步骤栏约 200px；在 1280px 宽窗口中，两栏已占约 35% 的横向空间。阶段二承接卡默认展开，即使没有成果，也列出五份“未生成”。

**影响**：用户需要同时理解“项目空间—五阶段—阶段内步骤—本步成果”。首屏空间花在解释结构上，本步输入和成果被向下挤压。

**建议**：

- 紧凑窗口默认收起交付物归档树，优先保留当前步骤。
- 承接卡默认显示一句摘要：“承接 3 份成果，2 个问题待确认”；点击后展开。
- 没有可承接内容时显示简短说明，不平铺五张不可操作卡片。
- 将文件路径放到详情中，主列表优先显示“需求与数据对接确认表”等业务名称。
- 保留底部固定主按钮；本次 1280×800 截图中主操作仍然可见，这是有效的设计。

证据：[阶段二 1280×800](stage2-1280.png)。

### 4.5 技能和知识：内容丰富，命名与分类需要治理

**观察**：从当前内置清单加载出 33 项技能、43 份知识文档。部分技能仍显示 `fde-business-flow`、`fde-data-flow` 等技术 ID；18 项技能进入“通用工具”。知识列表存在不同阶段同名的“产品原型Demo”。

**建议**：

- 所有面向用户的技能用中文业务名，技术 ID 保留在详情。
- 增加“适用阶段、输入要求、输出成果”，并按当前项目阶段推荐。
- 区分“模板 / 示例 / 项目实例”；同名原型注明“阶段二探索版 / 阶段三定稿版”。
- 统一技能来源、版本和内置标识，减少“未标注”“本地导入”造成的理解成本。
- 在项目任务里直接调用适用技能，减少跳到技能中心再找入口。

证据：[技能中心](skills-populated.png)、[知识中心](knowledge-populated.png)。

## 五、BUG 与可靠性问题清单

**优先级定义**：P1 为会影响核心任务、项目归属或状态真实性的问题；P2 为明显增加理解或恢复成本的问题。本次没有确认需要定义为 P0 的全面不可用问题。

### B01｜不同项目创建后可能打开同一个旧项目 — P1

- **证据类型：实际创建处理函数的隔离复现。**
- 操作：依次创建“为甲医院建设AI运营分析平台”和“为乙医院建设AI人事管理平台”。
- 实际：二者目录都为 `ai`，第二次返回甲医院的项目名称与需求，最终只有一个项目。`CRM客户管理系统一期/二期` 同样都转为 `crm`。
- 原因：`slugify()` 去掉中文，只留下英文；创建时目录已存在且有元信息，就直接返回旧项目。
- 影响：用户以为新建成功，后续可能在错误客户项目中继续工作；本次复现未发生已有文件覆盖。
- 建议：项目 ID 使用 UUID 或随机唯一后缀，显示名称与目录身份分离。显式的重复项目选择应有明确反馈。
- 验收：相同英文片段、相同显示名、长中文名均可创建独立项目；返回的需求与本次输入一致。
- 定位：`src/main/index.js:1240–1247、3672–3682`；`src/renderer/pages/projects/ProjectCreate.vue:78–81`。

### B02｜创建中途失败后，恢复服务仍可能无法重试 — P1

- **证据类型：实际创建处理函数的隔离复现。**
- 操作：创建 `CRM客户管理一期`，在 ACP `session/new` 时模拟失败；恢复服务后使用原内容重试。
- 实际：第一次提示引擎异常；第二次报 `Project "crm" already exists`。
- 原因：先建项目目录，再调用引擎，最后才写元信息；异常时留下无元信息的目录。
- 建议：先建立可恢复的项目记录，将引擎会话作为后续可重试步骤；或使用明确的创建中状态。清理时只处理本次操作创建且确认无用户成果的内容。
- 验收：创建期间断开引擎，再恢复后重试，应获得一个可继续使用的项目；不能因残留目录永久卡住。
- 定位：`src/main/index.js:3678–3689、3707–3739、3743–3745`。

### B03｜项目读取失败被显示为“还没有 FDE 项目” — P1

- **证据类型：前端接口失败模拟复现。**
- 操作：让 `listProjects` 抛出错误，打开项目列表。
- 实际：页面显示“还没有 FDE 项目”，引导新建，未显示失败原因和重试按钮。
- 影响：用户可能误以为项目丢失，或重复创建项目。
- 建议：分别实现加载中、读取失败、确实为空、有数据四种状态；失败时保留上次成功数据并允许重试。
- 验收：断开服务不能显示“0 项目”的确定性结论；服务恢复后可原地重新加载。
- 定位：`src/renderer/pages/projects/ProjectList.vue:225–235`。
- 截图：[读取失败后的错误空状态](list-error-empty.png)。

### B04｜新建失败只有控制台日志，用户看不到原因 — P2

- **证据类型：前端异常模拟复现；与主进程抛错返回方式一致。**
- 操作：填写需求并创建，让接口抛出错误。
- 实际：按钮恢复，输入保留，但页面没有错误说明；用户不知道是否成功、该如何恢复。
- 补充：当接口返回 `{ success:false }` 而非抛错时，按钮持续“正在创建”。这是额外的返回契约兼容问题；当前桌面创建处理函数主要通过抛错报告失败。
- 建议：设置可见错误状态；所有结束分支在 `finally` 释放提交态；异常响应也作为失败处理。
- 验收：网络异常、引擎异常和无 slug 返回均能结束加载，说明失败原因，并允许保留原输入重试。
- 定位：`src/renderer/pages/projects/ProjectCreate.vue:72–86`。

### B05｜阶段未完成，交接页却提示“五个步骤都已完成” — P1

- **证据类型：前端交互复现 + 流程函数复现。**
- 操作：打开阶段一，直接点击第 5 步“进入阶段二”，不执行资料收集、AI 解析和访谈摸底；仅填目标后也可复现。
- 实际：左侧步骤仍为“未开始”，成果显示“未生成”，中间却显示绿色成功提示。
- 原因：`gaps` 只统计已跳过和部分完成，没有包含 `todo/doing`；界面用“没有 gaps”代替“全部已完成”。
- 影响：用户对阶段完整度和交接质量形成错误判断，交接缺口也可能记录不全。
- 建议：分别计算“已完成、显式跳过、未开始、进行中”；未开始也纳入交接缺口。提示应为“已完成 1/4 项准备，可携带 3 项待补充进入下一阶段”。
- 验收：从任意步骤直接打开交接页，显示的完成数、缺口与实际一致；尚未发生的交接本身不能提前算完成。
- 定位：`src/renderer/data/stage1-research.mjs:74–88`；`src/renderer/components/projects/Stage1ResearchWorkspace.vue:151–160、502`。
- 截图：[未完成却提示完成](stage1-premature-completion.png)、[仅填写目标后的状态](stage1-goal-only-completion.png)。

### B06｜“目标必填”和实际推进条件不一致 — P1

- **证据类型：前端交互复现 + 前后端条件核对。**
- 操作：目标为空，直接进入交接页，只填写负责人。
- 实际：确认按钮可用；确认函数只检查负责人，阶段一后端校验也没有检查目标。
- 矛盾：界面将目标标为必填，数据层也写明只有目标必填；另一个建议函数却允许负责人直接确认。
- 建议：产品先明确唯一规则。若必须有目标，前后端共同校验；若允许负责人例外推进，就明确显示“携带缺口进入”，记录理由，不再宣称必填或全部完成。
- 验收：空目标场景有唯一、可解释的处理结果，任何入口都遵循同一规则。
- 定位：`Stage1ResearchWorkspace.vue:55、296、497–510`；`stage1-research.mjs:64、176–186`；`src/main/product-flow-gate.js:10–19`。

## 六、视觉观感建议

### 6.1 提高可读性，保留清爽感

辅助说明、表格简介和小标签普遍偏浅，部分字号为 10–12px。在投屏、低亮度屏幕和长时间阅读文档时，理解成本会增加。

- 正文建议 14–16px，表格主要内容 13–14px；关键提示避免使用占位文字的灰度。
- 先统一主文字、辅助文字、占位文字、禁用文字四级颜色。
- 常规小字号文本以 4.5:1 对比度作为验收目标；这是建议标准，本次未完成全站对比度自动审计。
- 成功/警告颜色要对应真实状态；修正 B05 的价值高于继续润色绿色提示框。

### 6.2 统一工作页面的组件语言

首页及资源中心使用较轻的蓝色卡片，阶段工作流更接近 TDesign 的灰底、表单与提示条。两者都清楚，但跳转后密度、灰度与按钮气质存在差异。

- 统一按钮高度、输入框高度、卡片间距、页面标题层级和状态标签。
- 页面只突出一个主要动作；“刷新、查看说明、更多”降为次要操作。
- 区分当前选中、鼠标悬停、键盘焦点，不让多个导航同时看起来像当前位置。

### 6.3 教练页：把展示空间转为练习信息

教练形象有记忆点，但初始大横幅与中部留白占比较高，底部“代码模式”等能力又会分散陪练目标。

- 首次进入保留形象介绍，后续折叠为紧凑头部。
- 提供“本次目标 / 客户角色 / 难度 / 预计轮次”，以及明确的“开始练习”。
- 对话中提供“结束并复盘”，让评分标准、关键问题遗漏和下一次训练建议有稳定落点。
- 支持把真实项目背景带入陪练，复盘结论再关联回项目。
- 语音效果和复盘质量需要真实模型条件下另行测量。

### 6.4 空状态应当帮助继续，而不是只占位

资源中心有数据时三栏布局有效；为空、未加载或未选择时，三栏同时留白会放大“没有内容”的感受。

- 读取失败：展示原因与重试。
- 确实为空：提供导入样例或创建首项。
- 搜索无结果：提供清除筛选。
- 尚未选择：右侧显示如何使用当前资源的简短说明，或临时收起。

## 七、流程化优化：建立一条可追踪的项目主线

### 7.1 每一步统一回答六个问题

> **当前目标 → 我需要提供什么 → 系统会做什么 → 会形成什么 → 谁来核对 → 下一步是什么**

把这六项固定在任务页，而不是让用户从阶段规范、技能描述和交付物模板中自行拼接。

### 7.2 推荐的五阶段体验

| 阶段 | 推荐主操作 | 成果与推进依据 |
|---|---|---|
| ① 调研准备 | 写目标 → 收资料 → 整理已知与待确认 → 准备访谈 | 已知事实、假设、问题清单、访谈资料；缺口允许携带但必须真实记录 |
| ② 需求沟通 | 导入本轮纪要 → 更新对接表 → 明确 AI 能力 → 演示原型 → 记录反馈 | 三项正式交付物；方向认可有确认人、依据和对应版本 |
| ③ 需求确认 | 确定首版范围 → 完善方案 → PRD/原型一致性检查 → 交接 | 产品成果完整、研发接收有记录、技术未验证项清楚 |
| ④ 工作台上线 | 交接跟进 → 实施问题处理 → 联调与上线验收 | 产品经理看到里程碑、负责人和阻塞；技术验证以真实记录为准 |
| ⑤ 客户试用 | 收集反馈 → 判断影响 → 迭代验证 → 定稿归档 | 反馈关联需求、版本和解决结果，形成可复用模板 |

当前任务化界面集中在前三阶段。建议把第四、五阶段在本产品中的责任明确表达为“实施协同 / 客户试用与交付管理”，并展示与执行团队的交接状态。避免用户仅因看到五阶段导航，就认为所有实施能力已经完成同等深度的产品化。

### 7.3 统一任务、文档和阶段状态

建议采用如下用户可见语义：

`待开始 → 资料待补充 → AI 处理中 → 待人工核对 → 已确认 → 上游变化需复核`

失败是可恢复的独立状态；显式跳过与未开始也需要区分。文档存在只代表有文件，不等于已核对，更不等于阶段完成。

首页待办、项目概览、交付物徽章、步骤页和交接页应读取同一套任务结论。目前已有 `state.json`、项目阶段状态、交付物确认记录及阶段一上下文，可以保留各自职责，但需要明确权威来源与同步规则。

### 7.4 将“缺口”变成可处理的问题

当前“标为已解决”主要更新状态与时间。建议问题至少具有：

- 稳定问题 ID；
- 问题内容与关联需求/文档；
- 负责人；
- 处理状态；
- 实际答案与依据；
- 对交付和推进的影响。

这样，“解决一个问题”才能自然更新需求与成果，而不是仅让列表中的一行消失。

### 7.5 明确自动保存与中断恢复

- 在编辑区统一显示“保存中 / 已保存 / 保存失败”。
- 切换步骤、项目或关闭窗口时，要能解释最后一次修改是否已保存。
- AI 任务呈现当前动作、已耗时、已产出内容、停止和继续入口。
- 重新生成前显示改动范围，完成后优先展示“变了什么、还需确认什么”。
- 跨阶段修改时告诉用户具体影响哪些成果，避免把所有内容一概打回而让用户无从下手。

## 八、建议落地顺序

以下是推荐迭代顺序，不是已经评估过的人力工期。

### 第一批：修核心可靠性

1. B01 项目唯一 ID 与命名冲突。
2. B02 创建失败恢复。
3. B03/B04 列表和新建的可见错误状态。
4. B05/B06 阶段一完成判定、缺口记录与目标规则。
5. 补充验证 R01 首次需求带入、R02 问题回写。

**验收重点**：项目不混淆；失败可恢复；进度不虚报；用户输入可保留。

### 第二批：提高日常效率

1. 首页突出当前任务与阻塞。
2. 项目默认进入本地成果空间，飞书入口明确标识。
3. 统一阶段名、技能中文名和成果名。
4. 精简双侧栏和阶段承接卡。
5. 统一保存提示、空状态和重试模式。

**验收重点**：用户能迅速找到下一步，理解文件与任务的关系。

### 第三批：强化长期价值

1. 问题、需求、原型、反馈、确认依据形成可追踪关联。
2. 研发交接包与阶段四、五协同状态串联。
3. 提供示例项目和行业模板。
4. 教练复盘与真实项目互通。
5. 按任务记录采用率、修改成本和交付周期。

## 九、验证结果与后续测试建议

### 本次已执行的现有测试

| 测试文件 | 结果 | 解读 |
|---|---|---|
| `scripts/test-stage1-research.mjs` | 14/14 通过 | 当前覆盖的调研、模板、承接与规则检查通过；未覆盖直接跳交接页的错误完成提示 |
| `scripts/test-project-flow.mjs` | 8/9 通过 | 一个用例期待旧样例通过阶段门禁，但当前格式校验拒绝其不合规范的内容；需更新样例和预期 |
| `scripts/test-stage2-contract.mjs` | 3/4 通过 | 一个用例因缺失 `scripts/fixtures/stage2-format/input.json` 无法执行 |

这两个失败说明回归基线尚不完整；不能据此断言真实用户的合规交付物必然无法推进。隔离页面体验脚本未捕获未处理页面异常，但这也不等于业务行为全部正确。

### 建议补齐的验收场景

- 连续创建含相同 `AI/CRM` 字样的不同客户项目。
- 新建过程中引擎失败，恢复后用原内容重试。
- 项目列表读失败、技能/知识读取失败与确实无数据的区分。
- 新建需求完整带入阶段一，切换后不丢失。
- 从第 1 步直接进入交接，缺口和状态真实。
- 上游修改后，下游状态、首页待办与项目概览同步。
- AI 运行中另一个窗口解决问题，答案回写不发生编号错配。
- 真实桌面下验证模型超时、取消、恢复、原型预览与 Word 导出。

### 建议度量的产品指标

以下是待建立的衡量方式，本次没有真实用户基线：

| 指标 | 衡量方式 |
|---|---|
| 首次有效成果时间 | 从创建项目到得到第一份用户愿意保留的成果 |
| 找到下一步的时间 | 新用户能否在建议的 10 秒内定位当前应做事项 |
| 核心任务完成率 | 无人工帮助完成“建项目—录纪要—形成成果—核对”的比例 |
| 失败恢复成功率 | 一次异常后，保留输入并重试成功的比例 |
| 交付物修改成本 | 用户从 AI 初稿到可交付版本的修改轮数和用时 |
| 状态一致性 | 同一项目在首页、列表、任务页、交接页是否给出一致结论 |

## 十、最终建议

**FDE 产设大师最有价值的方向，是把方法、资料、AI 能力和客户确认组织成用户能顺利完成的项目过程。**

当前已经具备方法论和成果体系，优先补齐创建可靠性、状态真实性与任务引导，会比继续增加入口或美化横幅更直接地提升体验。

建议用一句话作为后续每个页面的评审标准：

> 用户是否知道自己正在做什么、结果是否可信、遇到问题后如何继续？
