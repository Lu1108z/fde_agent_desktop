# FDE 产设大师｜改版后产品体验复评

**复评日期：2026-11-03**  
**评估对象：当前工作区源码，package.json 版本仍为 3.3.12**  
**对比基线：[2026-11-02 首轮报告](../fde-experience-audit-2026-11-02/产品体验分析报告.md)**

## 一、结论先行

**这次改版的实质进步是：后半段项目流程补齐了，宣传与演示场景更完整了；日常使用的可靠性和跨模块一致性仍需集中修整。**

新版比上一轮更像一个覆盖“项目推进＋资料展示＋行业方案演示”的工作平台。阶段四、五已进入统一步骤工作台，这是本轮最有价值的提升。宣传物料的卡片、原版式 Word 预览和直接下载，也贴近 FDE 面向客户讲方案的工作场景。

不过，**功能覆盖扩大不等于体验闭环已经完成**：上一轮六项问题仍能复现；新发现的回收站入口缺失、搜索上下文错位、验收后状态不一致，会影响用户对产品的信任。

### 相比上一轮的判断

| 维度 | 变化 | 复评结论 |
|---|---|---|
| 流程覆盖 | **明显提升** | 阶段二至五可在模拟 AI 产出的流程中连续推进至完成 |
| 客户展示能力 | **明显提升** | 新增宣传物料、页式文档预览和医院智能体演示平台 |
| 操作一致性 | **局部提升** | 阶段二至五的步骤结构统一；项目、宣传、平台的“智能体”概念仍分离 |
| 视觉观感 | **局部提升** | 新物料页清爽，文档阅读更正式；大屏与工作区切换反差较大 |
| 状态可信度 | **尚未明显改善** | 阶段一误报完成仍在；验收后修改出现新的完成状态矛盾 |
| 异常恢复 | **尚未明显改善** | 项目创建/读取异常未解决；物料恢复能力尚未形成用户可达的闭环 |

**建议下一次迭代集中做一次“可靠性与一致性收尾”，优先于继续增加顶级入口。**

## 二、本次评估怎么做的

- 重新体验工作台、新建项目、阶段说明、阶段一/二/四/五、知识中心、技能中心、教练与设置等页面。
- 用上一轮相同隔离样例复查创建失败、项目读取失败、阶段一交接问题。
- 运行实际项目创建处理函数，复现目录命名冲突和引擎失败后的重试问题。
- 运行阶段二至五交互测试：AI 输出由测试代码模拟，项目成果实际写入临时目录。
- 宣传物料使用真实本地资料库模块和 Word 文件，验证创建、上传、筛选、预览、下载、删除及底层恢复。
- 对宣传物料追加跨文件夹搜索检查；对已完成项目追加“修改成果后重新打开”检查。
- 智能体平台使用当前 `med-ai-demo` 资源和真实本地静态服务加载，查看运营大屏与智能体总览。
- 检查跨阶段复核传播、回收站路由、平台统计口径及相关实现。

### 测试边界

项目和授权等接口使用隔离样例。真实模型生成质量、语音效果、安装包授权、飞书/极库云登录仍未完成桌面端端到端验证。本次宣传物料测试实际上传的是 **1 份 DOCX**；测试脚本虽包含 PPT 和视频分支，但本次未提供对应样例，**不能把它们记为已通过**。

智能体平台是当前集成的静态演示站，页面中的调用量、在线人数不能视为已接入真实医院的证明。

## 三、这次改得好的地方

### 3.1 阶段四、五终于有了可操作的任务主线

上一轮主要是前三阶段的任务化操作。本轮已经增加：

- **阶段四**：排定开发进度 → demo 走查 → 上线核对。
- **阶段五**：跟踪客户反馈 → 三轮迭代定稿 → 使用率盯防 → 项目交付签字。

输入、生成、成果查看、人工核对、阶段推进采用相同页面结构。模拟流程中，阶段二可以连续推进至阶段五完成，完成后也能回看阶段四/五文档。

**评价：这是产品流程的实质进步。** 用户不再需要在第三阶段后自行猜测工作如何接续。

另外，阶段四上线核对必须填写确认人和依据，前后端都有相应校验。第四、五阶段使用知识中心模板整理实际项目记录，也比纯粹的“让 AI 自己发挥”更可控。

证据：[阶段四](stage4.png)、[阶段五](stage5.png)。

### 3.2 宣传物料更贴近客户沟通场景

“按智能体分组 → 按类型筛选 → 点封面预览 → 下载”的结构容易理解。把 PPT、视频、Word、PDF 集中到同一处，符合售前演示与方案介绍需求。

本次已验证 Word 按纸张排版显示，下载文件字节数与原件一致，卡片与预览页均可发起下载。

**评价：页面用途清楚，业务收益直接。** 后续应重点补好搜索、版本、恢复，而不是增加更多装饰。

证据：[宣传物料列表](promo-populated.png)、[Word 页式预览](promo-word-preview.png)。

### 3.3 细节上的改进方向正确

- 输入框锁定条件与后台保存状态分开，代码中增加中文输入法组合输入保护；有助于减少自动保存对打字的干扰。本次未做完整中文输入法专项测试。
- 阶段一承接卡的标题和映射说明增加截断/提示处理，窄区溢出控制更细。
- 智能体平台加入页面缓存，切回时保持同一个 iframe 节点来源；代码上避免每次重新挂载，不必重复开始演示。

## 四、上一轮六项问题复查

**结论：六项问题在当前工作区仍未关闭。** 这不否定本轮新增能力的价值，但它们仍应是下一轮优先处理项。

| 原编号 | 问题 | 本轮结果 | 优先级 |
|---|---|---|---|
| B01 | 不同中文项目含相同 AI/CRM，创建后返回同一旧项目 | 实际创建函数重测，第二个医院项目仍返回第一个项目，项目数为 1 | P1 |
| B02 | 创建时引擎失败，残留目录阻止重试 | 恢复服务后仍报 `Project "crm" already exists` | P1 |
| B03 | 项目读取失败显示“还没有项目” | 页面故障注入仍复现 | P1 |
| B04 | 新建失败只有日志，无用户可见错误 | 抛错后无错误文案；返回无 slug 的失败对象时仍保持创建中 | P2 |
| B05 | 未完成阶段一却提示“五个步骤都已完成” | 直接打开交接页仍显示绿色完成提示 | P1 |
| B06 | 目标标为必填，但交接只检查负责人 | 空目标填写负责人后，确认按钮仍可用 | P1 |

证据：[创建函数复查记录](create-recheck.json)、[页面观察](observations.json)、[阶段一误报完成](stage1-premature-completion.png)、[读取失败空状态](list-error-empty.png)。

修复方向沿用首轮建议：唯一项目 ID、可恢复的创建事务、错误与空态分离、所有提交分支释放加载状态、真实计算未完成/跳过项、统一目标与例外推进规则。

## 五、本轮新发现的问题

### N01｜已验收项目修改后，仍显示“项目已验收完成” — P1

**验证方式：在完整流程测试后追加真实文件修改和页面重载。**

1. 完成阶段二至五，并点击“验收并完成项目”。
2. 修改 `stage5/delivery-sign.md` 的交付范围。
3. 重新打开项目。

**实际结果**：签字任务变成 `needs-review`，但项目 `stageStatus[5]` 仍为 `done`；页面继续显示“项目已验收完成”，没有再次“验收并完成项目”的按钮。首页进行中项目的过滤又依赖 `stageStatus[5]`，因此待复核项目可能不会重新出现于进行中列表。

**建议**：

- 保存“历史验收基线版本”和“当前工作版本”两套明确状态。
- 验收后修改时显示“已验收版本 v1；当前修改待复核”，或显式重开项目。
- 当前成果失效时恢复待办与重新验收入口。

**验收标准**：修改已验收内容后，首页、项目状态、任务状态和重新验收入口一致，不会同时宣称“本版已完成”和“本版待复核”。

定位：`ProjectFlowWorkspace.vue:55–56、197、308–315`；`ProjectDetail.vue:1357`；`data/workbench-projects.js:9–10`。

证据：[复现记录](completion-recheck.json)、[截图](completed-but-needs-review.png)。

### N02｜文档修改后的跨阶段复核传播不完整 — P1

**验证方式：实际 `createFlowService.refresh()` 函数隔离复现。**

在阶段三、四、五任务已确认时修改 PRD，刷新后：

- 阶段三定稿与交接 → 需复核；
- 阶段四 demo、上线及阶段五任务 → 仍已确认。

本轮 `invalidateFollowing()` 已扩展到后续阶段，这是进步；但文件指纹刷新路径仍只特殊处理了阶段二到三，两条路径的影响范围不一致。

**建议**：统一变更影响计算，文档编辑、外部文件修改、重新生成均调用同一套逻辑；按依赖指出受影响成果。无依赖的任务不必全部重做。

**验收标准**：已确认 PRD 的范围变化能标记相关走查与验收依据需复核，不因修改入口不同得到不同结果。

定位：`data/project-flow.mjs:119–142`，对比 `ProjectFlowWorkspace.vue:242–249`。

证据：[函数复现记录](downstream-recheck.json)。

### N03｜宣传物料“可在回收站恢复”，但用户找不到对应入口 — P1

**验证方式：真实资料库删除操作、页面导航及路由核对。**

删除物料后提示“已删除，可在资料库回收站恢复”。底层 `lib.restore()` 确实可恢复，本次测试通过；但当前本地 `Library.vue` 没有挂载到路由，`/library` 转到团队资料库，而团队资料库嵌入的是极库云。

**问题不是文件被永久删除，而是承诺的恢复路径用户不可达。**

**建议**：宣传物料页提供本地回收站入口，成功提示附“撤销 / 查看回收站”；恢复文件夹时说明其子物料的恢复规则。

**验收标准**：用户仅通过界面，能完成“删除物料 → 找回物料 → 重新预览”；不依赖开发者调用恢复函数。

定位：`PromoMaterials.vue:147–160`；`router/index.js:49–52`；`TeamLibrary.vue:2`。

### N04｜宣传物料搜索后，左侧结果与右侧内容不一致 — P2

**验证方式：两个智能体文件夹的真实资料库样例。**

当前选中“门诊运营助手”，搜索“排班方案”：左侧只剩“智能排班助手”，右侧标题仍是“门诊运营助手”，并提示“上传这个智能体的宣传物料”。手动点左侧搜索结果后，实际存在的文件才显示。

**影响**：用户会误以为搜索无结果或物料不存在；此时上传还可能落入原来选中的文件夹。

**建议**：全局搜索显示带所属智能体的结果；或自动选择第一个匹配智能体。无匹配时提示“没有搜索结果 / 清除搜索”，不要复用“尚未上传”的空状态。

**验收标准**：搜索、当前选中项、右侧标题、结果列表与上传目标保持一致。

定位：`PromoMaterials.vue:98–112、121`。

证据：[搜索错位截图](promo-search-mismatch.png)、[操作记录](new-module-observations.json)。

### N05｜智能体平台大屏与总览统计口径不一致 — P2

**验证方式：本地静态平台页面读取，并核对总览统计定义。**

- 大屏：**17 个智能体，完成 3 / 开发中 14**。
- 总览动画结束后的页面数据：**18 个智能体，已上线 4 / 建设中 14**。
- 总览卡片通过“是否有页面 URL”判断“在线”，所以有页面入口的卡片都可显示“实时运行中”，与业务上线状态并非同一概念。

**建议**：从统一智能体目录计算数量；分开定义“有可演示页面、建设中、已部署、运行在线”。演示页面明确标注样例数据与演示状态。

**验收标准**：同一版本两个页面的总数及分类一致；“页面能打开”不能自动解释为“服务运行在线”。

定位：`med-ai-demo/index.html:223、334–336`；大屏当前静态资源。总览截图可能包含数字动画中间帧，本文结论以动画结束后的 DOM 数据和定义为准。

证据：[平台观察记录](new-module-observations.json)。

## 六、视觉观感与信息架构复评

### 6.1 新工作流：一致性提高，重复层级仍偏多

阶段二至五已经统一为“步骤导航＋当前任务卡”，学习一次后可迁移，这是有效改进。但左侧仍同时存在项目导航、五阶段树和当前阶段步骤栏。

**建议**：

- 1280px 窗口优先显示当前步骤，交付物树默认紧凑或可折叠。
- 当前任务标题不用在步骤栏、步骤小标题、主标题中反复强调。
- 主区域增加本阶段整体摘要：“完成 1/3 步，尚有 2 项待研发确认”。
- 阶段二没有承接成果时压缩承接卡，不用五张“未生成”卡片占据首屏。

### 6.2 宣传物料：清晰度不错，需减少概念与操作歧义

卡片按类型着色、标题与文件大小分层，适合快速浏览；Word 页式预览也明显增强正式感。

进一步建议：

- “新建智能体”实际创建的是物料文件夹，改成 **“新建智能体资料夹”** 或“添加物料分组”。
- 添加发布版本、更新时间和适用场景，帮助用户辨别“给哪个客户看哪一份”。
- 预览页上层“下载到本地”和阅读器“导出 Word”重复，且容易让用户以为两者产物不同；统一为“下载原件”。
- 危险操作收进“更多”，主路径突出预览和下载。
- 空文件夹、搜索无结果、读取失败使用不同说明。
- 自动缩放 Word 之外提供手动缩放和页码；长文档中查找更方便。

### 6.3 智能体平台：演示感染力强，日常使用信息过密

深蓝大屏、医生形象、指标排行和地图有展示效果。但作为 FDE 日常工作入口，第一屏首先展示大量运营指标，而不是告诉用户“这里有哪些可演示方案”。浅色总览更适合找具体智能体。

**建议**：

1. 默认进入“行业方案总览”，大屏作为“展示模式”。
2. 大屏保留演示视觉，收敛自动切换和动效，演示者能暂停、锁定某个智能体。
3. 明确“样例环境 / 演示数据”，避免和本地项目实际进度混淆。
4. 统一顶层返回与内部返回的命名；双层品牌导航只保留必要上下文。
5. 从方案卡直接访问相关宣传物料、原型和项目模板。

当前平台加载错误只有一行提示，没有重新加载入口；资源存在但 iframe 内部失败时，也缺少统一的错误恢复状态。建议补“重试 / 返回方案总览”。

证据：[平台大屏](agent-platform-dashboard.png)、[方案总览](agent-platform-overview.png)。

### 6.4 整体结构需要明确三种使用意图

当前同一产品里出现：

- 做客户项目：工作台、项目与交付物；
- 学方法、准备材料：培训、技能、知识、宣传物料；
- 给客户展示行业方案：智能体平台、AI 应用广场。

这三类都合理，但新增内容后，**“智能体”同时指技能、资料夹和平台方案**，用户需要自己分辨。

建议在现有导航中强化任务语言：

| 用户要做的事 | 建议表达 |
|---|---|
| 推进手头项目 | 项目工作台 / 我的项目 |
| 找客户演示案例 | 行业方案演示 |
| 找可发给客户的材料 | 宣传物料 |
| 找 AI 可调用能力 | 技能中心 |
| 看团队统一进度 | 团队进度 · 飞书 |

顶栏“项目”当前仍默认进入飞书，建议默认本地项目列表，让用户先进入可以直接开展工作的空间。

## 七、流程设计上下一步最值得改什么

### 7.1 让“生成表格”和“完成业务”对应起来

阶段四、五任务化已补齐，但当前主要操作仍是输入文字、生成文档、核对文档。实际项目管理还需要能直接查看未关闭反馈、延期里程碑和确认状态。

建议逐步增加结构化摘要：

- 进度表 → 里程碑日期、负责人、延期提醒；
- demo 走查 → 未通过项、复测证据；
- 反馈跟踪表 → 待处理/处理中/待客户验证/已关闭；
- 签字表 → 实际确认版本、确认人、依据与遗留问题。

文档继续保留作为交付物，首页待办从这些真实状态生成。

### 7.2 “使用率盯防”应允许成为持续跟进任务

目前 30/60/90 天使用率任务位于交付签字之前，且后续步骤依赖前面的核对。真实项目里回访周期往往跨越交付之后。

建议将“制定跟进计划”作为交付条件，将“完成第 30/60/90 天回访”作为交付后的持续任务。不要让用户为了签字把未来回访误标为完成。

### 7.3 统一研发接收与阶段推进的含义

当前第三阶段资料核对后可进入第四阶段，同时研发接收可能仍是“待接收”。这可以是有意允许的业务弹性，但需要清楚说明。

建议选择一种明确语义：

- 进入实施准备，保留“研发尚未接收”的显著待办；或
- 实施正式开始依赖研发接收记录。

关键是让用户知道“进入阶段四”究竟代表什么，避免阶段进度比真实协作进度更乐观。

### 7.4 把宣传与方案真正关联到项目

建议建立轻量关系：`方案 → 宣传物料 → 项目采用记录 → 需求差异 → 项目成果`。

示例：在“智能排班方案”里点击“基于此方案新建项目”，自动带入演示原型与宣传资料；后续记录客户的差异需求。这样新增展示模块才能直接提升项目推进效率。

## 八、建议落地顺序

### 第一批：核心可靠性与状态闭环

- 修复 B01/B02 项目身份冲突、创建失败恢复。
- 修复 B03/B04 可见错误状态。
- 修复 B05/B06 阶段一错误完成提示和规则矛盾。
- 修复 N01/N02 验收后修改与跨阶段复核。
- 补齐 N03 本地回收站入口。

**验收目标**：项目不混淆，失败可重试，修改后的状态不虚报，删除可由用户自行恢复。

### 第二批：统一用户理解

- 修 N04 搜索上下文，N05 平台统计口径。
- 区分“资料夹 / 技能 / 行业方案 / 已部署智能体”。
- 优化项目默认入口、双侧栏、空态和下载文案。
- 平台默认总览，明确演示环境及返回路径。

### 第三批：连接新增能力

- 方案与宣传物料、项目关联。
- 反馈与里程碑结构化。
- 交付后跟进任务可持续追踪。
- 真实桌面环境验证模型异常、PPT 放映、视频编码和长文档性能。

## 十、最终评价

**本轮改版值得肯定：五阶段的后半段可操作了，客户展示与材料准备能力也更完整。**

当前最有价值的下一步，是让“项目状态、文档状态、验收状态、恢复路径”真正一致，再把行业方案、宣传物料和实际项目连接起来。

一句话总结：**功能已经更完整，下一轮应让用户更放心地用它完成真实项目。**
