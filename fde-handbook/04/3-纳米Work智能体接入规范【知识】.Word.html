360 纳米 Work 行业 AI 工作台 · 智能体接入规范

阶段四【知识】。项目系统里的智能体怎么接、怎么管、怎么用，定一套统一规范。核心一句：智能体和引擎解耦——一个智能体可以同时挂多个引擎，项目里用一套标配页面统一管理和调用。

定位说明：这份讲的是行业智能体层（业务智能体挂哪个引擎、三个标配页面），跟真实仓库 ai-work-platform README 讲的平台底座层（多租户/调度/审计的通用后台）是两层，各管一段。技术落地口径（配置中心、日志落表、SSE 流式）以真实仓库为准。

一、智能体管理：一个智能体，多个引擎

核心设计：解耦

智能体（业务层，定义"这个智能体是干嘛的"）和执行引擎（能力层，实际跑智能体的平台）分开。一个智能体不绑死在某个引擎上，可以同时对接多个引擎。

          ┌─────────────────┐
          │   智能体（业务定义）  │  ← 名称、说明、能力、挂哪些引擎
          └────────┬────────┘
                   │ 一对多
        ┌──────────┼──────────┐
        ▼                     ▼
  ┌───────────┐        ┌───────────┐
  │ SeaFactory │        │   Dify    │   ← 执行引擎（可扩展）
  │ 360智能体平台 │        │           │
  └───────────┘        └───────────┘

为什么要一对多

  • 不被单一引擎绑死：SeaFactory 挂了能切 Dify，换引擎不用重配智能体
  • 按场景选引擎：同一个智能体，某些场景走 SeaFactory、某些走 Dify，各取所长
  • 平滑迁移/对比：同一智能体挂两个引擎，可以 A/B 对比效果，再决定主用哪个

二、支持的执行引擎

引擎 说明 接入方式
SeaFactory（360 智能体平台） 主力引擎，360 自研 平台 API / 连接器
Dify 开源 LLM 应用平台 Dify API

引擎可扩展。新增引擎时，按统一的引擎适配接口接入，不改上层智能体定义。

三、接入规范

  1. 智能体定义与引擎配置分离——智能体表存业务定义，引擎配置单独存，多对多关联
  2. 每个引擎一个适配器（adapter），统一接口（发起对话、流式返回、工具调用），上层不感知引擎差异
  3. 引擎的 base_url / api_key / 模型名走配置中心优先（数据库配置中心 A/B 档加载，.env 仅作兜底），禁止硬编码；不裸 os.getenv()，走 core/config.py 的 Settings
  4. 调用必须记录：走了哪个引擎、token 用量、耗时——落库便于计费和排查。落到 LLM 网关查询日志（log_mcp_queries 表，对应 /api/admin/mcp-query-logs 可检索/详情/导出/重跑）
  5. 一个智能体挂多引擎时，要有默认引擎 + 可指定引擎调用
  6. 引擎调用失败要有兜底：超时、重试、降级到备用引擎

四、标配页面（项目必须有的三个页面）

每个行业工作台项目都要标配下面三个智能体页面，作为统一入口。

页面 干什么 关键功能
① 智能体管理页 列出项目里所有智能体，能配置、挂引擎 智能体增删改查、给智能体挂/换引擎、启用停用、查看状态
② 智能体调用/测试页 选一个智能体，输入问题，看它回什么 选智能体、选引擎、输入对话、看实时返回（SSE 流式）、对比不同引擎效果
③ 智能体工具箱页 一堆现成智能体工具，点开就能用 智能体工具卡片墙，按场景分类，点开直接用，业务人员自助

三个页面是标配，不是选配。管理页给管理员配、测试页给开发调、工具箱页给业务用——三类人各有入口。

五、验收标准

  • 智能体和引擎解耦，一个智能体能挂多个引擎
  • SeaFactory、Dify 两个引擎都接通、能切换
  • 三个标配页面（管理/测试/工具箱）都有、都能用
  • 引擎配置走配置中心（数据库 A/B 档，.env 兜底），没硬编码 key
  • 调用有日志（引擎/token/耗时）落 log_mcp_queries 表，有失败兜底
  • 流式返回走 SSE（text/event-stream），不卡死页面
  • 换引擎不用改智能体定义
