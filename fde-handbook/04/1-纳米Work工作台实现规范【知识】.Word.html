纳米Work 工作台实现规范【知识】

定位：讲清楚阶段四怎么把智能体矩阵 + 产品原型变成能跑的前后端系统。核心讲三件事：上游交什么 → 数据模型怎么建 → 前后端怎么搭。

技术栈口径以真实仓库 ai-work-platform 为准：后端 FastAPI + SQLAlchemy2.0(async) + Pydantic2；前端 Vue3 + TS + Vben Admin5 + Element Plus；列表返回 {items,total}、单对象裸返回（无 Result 包装）；多租户强制 hospital_id 过滤；表前缀 sys_*/busi_*/log_*。下文 Prompt 模板里的技术约束一律照此，别用 Ant Design / {code,data,message} / leads_ 这类通用旧写法。

一、上游要求：阶段二、阶段三必须交付什么

AI 编程工具是放大器，不是造物主。上游给垃圾，下游出精致的垃圾。阶段二、阶段三提交的内容必须满足以下三样，缺一打回。

1.1 三样必交物

交付物 来源阶段 内容要求 验收标准
功能清单表 阶段二 每个页面/按钮/字段定义清楚，含优先级 P0/P1/P2 每条功能能追溯到需求文档，有验收标准
智能体矩阵设计 阶段三 智能体矩阵表 + 各智能体设计文档 + Prompt 库 + skill 清单 + 知识库配置 每个智能体五层拆解完整，准确率达标（≥90%）
真实业务数据样本 阶段一/客户 能覆盖核心业务场景的真实数据（脱敏后） 数据量够跑通主流程，字段跟 ER 模型对得上

1.2 功能清单验收标准（六字段，缺一不可）

字段 说明 缺失后果
功能名称 唯一识别，如工作台-001 无法在代码中追溯引用
所属页面 对应原型的哪个页面 开发不知道往哪个页面放
功能描述 一句话说清"用户做什么" AI 会脑补功能边界
优先级 P0 必须 / P1 重要 / P2 可选 AI 无法决定开发先后
关联智能体 对应阶段三的哪个智能体 工作台不知道调哪个智能体
数据依赖 需要哪些数据表/字段 ER 模型建不全

⚠️ 上游红线：缺少"关联智能体"或"数据依赖"的功能，实现岗有权打回。这两项是 ER 建模和工作台开发的根基，缺了就是让 AI 在真空中写代码。

1.3 智能体矩阵交接模板

阶段三交付时，按以下格式交接，保证阶段四能直接用：

【智能体矩阵总览】 —— 智能体名称 / 负责环节 / 输入 / 输出 / 挂载 skill / 挂载知识库 / 准确率

【各智能体设计文档】 —— 每个智能体填好的《智能体设计表》：身份卡、五层拆解、六组件、Prompt、知识库、Skill、A/B 测试、验收检查表，缺一不可。

【Prompt 库】 —— 每个智能体的完整 Prompt，含角色、任务、输入、规则、输出格式、约束。

【skill 清单】 —— skill 名称 / 干什么 / 调用方式 / 输入参数 / 输出格式 / 错误处理。

二、ER 数据建模：从功能清单到数据模型

拿到功能清单和智能体矩阵后，不要直接让 AI 写代码。先做三步：实体识别 → 关系建模 → 数据演练。

2.1 第一步：实体识别（从功能清单反推数据表）

把功能清单里出现的每个"名词"——用户、订单、客户、合同——都提出来，这就是实体。每个实体一张表。

实体识别 Prompt 模板（填完这个再让 AI 生成建表 SQL）：

【角色】数据架构师，10年行业系统建模经验
【任务】基于以下功能清单，识别所有业务实体并输出 ER 模型
【输入】功能清单：{粘贴}
【规则】
1. 每个业务名词一张表，不拆不漏
2. 标注实体间关系（1:1 / 1:N / N:N），N:N 必建中间表
3. 每个实体列出核心字段（≤15个），标注类型、是否必填、默认值
4. 识别外键关联
5. 区分业务实体和日志实体（操作日志、会话记录单独建表）
【输出格式】
| 实体名 | 表名 | 核心字段（含类型） | 关联实体 | 关系类型 | 外键 |
【约束】
- 字段名用英文蛇形命名（snake_case）
- 表名复数、加前缀：系统表 sys_、业务表 busi_、日志表 log_（照真实仓库口径，不用 leads_/cust_ 这类临时前缀）
- 每张业务表必带：id（UUID）、hospital_id（多租户）、created_at、updated_at；软删除用 deleted_at
- 时间字段统一用 datetime/timestamp，不用 varchar 存时间

实体四要素：

要素 说明 示例
实体名 业务名词，不是数据库表名 客户、智能体会话
属性 实体有哪些字段 客户：客户ID、来源、行业、状态…
关系 跟谁有关联 会话→客户（多对一）
约束 唯一性、非空、默认值 客户ID唯一非空，状态默认"待跟进"

2.2 第二步：关系建模（画出 ER 图，验证业务逻辑）

把实体和关系画成 ER 图，验证业务逻辑能不能跑通。这一步必须拿真实数据演练——不是画完就完了，要用样本数据走一遍核心流程，看数据能不能流转起来。

关系建模四维校验：

检查维度 检查问 不通过的典型表现
完整性 核心流程的数据链路是否打通？ 客户→合同，中间断了一截
一致性 同一字段在不同表中的定义是否一致？ 客户ID在A表int、B表varchar
冗余性 有没有重复存储的字段？ 客户名称在订单表和客户表各存一份
可扩展 加新行业时能不能加字段不改结构？ 换行业要改表结构

2.3 第三步：数据演练（拿真实数据跑一遍）

步骤 做什么 产出
① 灌样本数据 把阶段一拿到的真实数据（脱敏后）灌进表里 有数据的数据库
② 走核心流程 按功能清单的核心链路走一遍 每步的数据流转记录
③ 找断点 哪里数据接不上、字段缺了、类型不对 断点清单
④ 补模型 根据断点修改 ER 模型 修正后的 ER 图

⚠️ 数据演练红线：没有拿真实数据走过一遍的 ER 模型，不允许进入开发阶段。纸上画得再漂亮，数据跑不通就是废纸。真实数据的脏数据、缺字段、格式不一致才是上线后真正的坑。

三、前后端怎么搭：AI 编程工具 + 平台标准 skill

3.1 两步法：先 demo，再完整

为什么先 demo：demo 能拿去给客户演示、拿反馈，不用等全部做完才知道方向对不对。这是 FDE 体系的"快速验证"思路——先验证大方向，再抠细节。

步骤 目标 范围 产出
第一步：还原 demo 核心流程能演示 P0 功能 + 核心页面 + 主链路打通 demo 系统
第二步：补齐完整 能上线 P0+P1 全部 + 异常处理 + 权限 + 部署 完整工作台

3.2 平台标准 skill：64 个不用从零开发的模块

仓库 .claude/skills/ 里沉淀了 64 个 skill = api-* 32 + vben-* 32（另有 api-guide/vben-guide 两个合集大指南），用 Claude Code 打开项目自动加载。阶段三设计的智能体，挂载的 skill 分为两类：

skill 类型 来源 使用方式 举例
平台标准 skill 仓库已有的 64 个开发规范/生成器 直接照着生成，不重复造轮子 api-router/model/migration、vben-crud/table/form
行业定制 skill 阶段三按行业需求设计 按设计文档开发 行业数据查询、行业报告生成

skill 配置规则：

  • 优先用平台标准 skill——64 个已有的先翻一遍，能用的不自己写
  • 行业定制 skill 按阶段三设计文档开发——不脱离设计文档自创
  • 每个 skill 单一职责——一个 skill 只干一件事，不混装
  • 每个 skill 有错误处理——调用失败有兜底，不崩页面

3.3 AI 编程工具使用规范

工具 适用场景 使用要点
Claude Code 前端页面生成、组件开发、后端服务 打开项目自动加载 skills；给六区块 Prompt，锁定 Vben/Element Plus 组件库
360 WisCode 后端服务、API 开发 先出接口文档再写代码，接口跟 ER 模型对齐
Codex 批量生成、脚手架 项目初始化、模板代码批量生成

3.4 前端开发 Prompt 模板（六区块法 + 智能体挂载）

【区块1·页面定位】
页面名称：{xxx}  所属模块：{xxx}
页面类型：☐列表页 ☐详情页 ☐表单页 ☐Dashboard ☐弹窗
优先级：P{0/1/2}
【区块2·角色与入口】
使用角色：{角色}，权限：{权限级别}
入口路径：从{哪个页面}通过{什么操作}进入
【区块3·功能区清单】
本页功能区（≤5个），按主次排序：
1. {功能区名} — {职责} — 调用智能体：{xxx} — 主/次
【区块4·布局规范】
组件库：Vben Admin 5 + Element Plus（@vben/web-ele）— 锁死，不用 Ant Design/Arco/Semi
栅格：Element Plus 24 栏栅格，内容区宽度 {xxx}px
视觉风格：☐企业级后台 ☐数据大屏（颜色引用 Theme Token，不硬编码）
【区块5·交互规则】
- {操作} → 调用{skill/api} → {反馈} → {跳转}
- {异常} → {提示方式}
【区块6·边界条件】
- 空数据/加载中/权限不足/数据超长/并发操作/网络异常 各状态表现
【开发约束】
- 只动 apps/web-ele/src/，禁改 packages/@vben/*
- 网络请求走 requestClient（@vben/request），禁裸 axios/fetch
- 只用 <script setup>，类型定义放 src/types/api/<module>.ts
- 智能体调用超时：前端显示"智能体处理中"，不卡死页面

3.5 后端开发 Prompt 模板

【角色】后端架构师
【任务】基于 ER 模型，生成后端 API 服务
【输入】
- ER 模型：{粘贴}
- 功能清单：{粘贴}
- 智能体矩阵：{粘贴}
【规则】
1. 按 RESTful 规范设计接口，路由前缀 /api/<entities>
2. 每个实体一套 CRUD 接口 + 业务接口
3. 智能体调用接口单独封装，不跟业务接口混
4. 所有接口做参数校验和异常处理
5. 返回格式：列表 {"items":[...],"total":N}，单对象裸返回（不加 code/data/message 包装）；错误 raise HTTPException(status_code, detail="中文说明")
【输出】
1. 接口文档（按实体分组，含请求/响应示例）
2. Alembic 迁移（autogenerate 后人工复核 SQL）
3. 后端服务代码（分层 api→services→managers→db）
【约束】
- 每个 .py 首行 from __future__ import annotations；全量类型注解
- api/ 层不写 SQL；业务查询强制带 hospital_id 过滤
- 不裸 os.getenv()，走 core/config.py 的 Settings
- 智能体调用超时设 30s，超时返回"处理中"状态
- 敏感数据脱敏返回（手机号、身份证号）；日志用 loguru，记录每次智能体调用入参/出参/耗时

四、五层拆解：工作台实现的完整流程

跟智能体设计模板对齐，把工作台实现拆成五层。

  • ① Workflow（整个活的流程）：拿到功能清单和智能体矩阵 → ER 建模 → 数据演练 → demo 开发 → demo 验证 → 完整开发 → 部署上线
  • ② 节点（每一步的细节）
节点 输入从哪来 做什么处理 输出什么
ER 建模 功能清单 + 智能体矩阵 实体识别 + 关系建模 ER 模型图
数据演练 ER 模型 + 真实数据样本 灌数据 + 走核心流程 断点清单 + 修正 ER 图
demo 开发 修正 ER 图 + P0 功能清单 AI 编程工具生成前后端 demo 系统
demo 验证 demo 系统 业务方/客户演示 反馈清单
完整开发 demo 系统 + P1 功能清单 + 反馈 补齐功能 + 异常处理 + 权限 完整工作台
部署 完整工作台 极库云流水线 + 容器云 可运行的生产系统
  • ③ Playbook（每一步怎么做、规则是什么）
节点 判断规则 / 执行策略
ER 建模 名词提取法，功能清单里每个业务名词都是候选实体；会话、操作日志单独建 log_ 表，不跟业务表混
数据演练 必须用真实数据——真实数据的脏数据、缺字段、格式不一致才是真问题
demo 开发 只做 P0——目的是验证方向，能演示核心链路就行
智能体挂载 优先用平台标准 skill——64 个已有的先翻一遍，不够的再开发行业定制 skill
AI 编程 锁定组件库（Vben/Element Plus）+ 栅格 + 视觉风格——不锁，AI 每次生成风格都不一样
完整开发 异常处理必须覆盖五类——输入/输出/权限/并发/异常
智能体调用 复杂分析用异步轮询，简单查询用同步——超过 5 秒的分析不能让用户干等
  • ④ 边界（管到哪儿为止）：阶段四不重新设计智能体，只负责把设计好的智能体挂上去、跑起来。
  • ⑤ 异常（出岔子怎么办）
异常场景 兜底策略
ER 模型跑不通 标注断点，跟业务方确认是数据问题还是模型问题，不硬改
智能体调用超时 前端显示"智能体处理中"，后端异步轮询，30s 超时返回失败状态
AI 代码编译不过 人审报错，手动修复，不反复让 AI 重试超过 3 次
平台 skill 不可用 标注"功能暂不可用"，不假装能用
数据库迁移失败 回滚到上一个稳定版本，不硬推
智能体返回脏数据 后端做数据校验，脏数据不透传到前端，返回"数据异常"提示

五、智能体挂载配置

工作台的每个功能页面，都要挂载阶段三设计的智能体。这是工作台和智能体的接口规范。智能体接入的详细规范（多引擎解耦、三个标配页面）见《3-智能体接入规范》。

六组件配置清单：

组件 配置内容 备注
① 角色（Expert） 按阶段三智能体矩阵配置 每个智能体的专家身份，直接复用不改
② 提示词（Prompt） 按阶段三 Prompt 库配置 直接复用阶段三定稿的 Prompt
③ 知识库 按阶段三知识库配置清单 行业知识库 + 内部数据，注意数据权限
④ 技能（Skill） 平台标准 skill + 行业定制 skill 64 个标准优先，定制按设计文档开发
⑤ 工具/连接器 按 ER 模型配置数据源 HIS/CRM/线索库等，跟数据库对接
⑥ 记忆（Memory） 配置会话上下文记忆 记住用户操作历史，跨页面保持上下文

要点：阶段四不重新设计智能体，是把阶段三设计好的智能体挂到工作台上。智能体的设计归阶段三，工作台归阶段四，职责不混。

六、部署与交付

6.1 部署走 CI/CD 流水线

线上发布走 极库云流水线 → 360 智汇云容器云，不用本地 docker compose。极库云为三个服务各配一条流水线（api=22530 / scheduler=22531 / frontend=22532），点「运行」一键发布：代码源 → 构建容器云镜像 → 容器云发布，全绿即成功。发布后进容器云 CIS 看三个 Deployment 的 Pod 状态、日志。

6.2 交付物清单

交付物 内容 验收标准
ER 模型图 数据库表关系图 核心流程数据跑通
demo 系统 核心流程可演示 P0 功能全通
完整工作台 P0+P1 功能完整 能上线运行
部署文档 环境配置 + 部署步骤 按文档能独立部署

智能体配置 智能体矩阵已挂载 准确率达标

七、交付前终检清单

  • 上游三样齐全（功能清单 + 智能体矩阵 + 真实数据样本）
  • 功能清单六字段完整，每条功能有"关联智能体"和"数据依赖"
  • ER 模型已出，四维校验通过（完整/一致/冗余/可扩展）
  • 数据演练跑通——真实数据走过核心流程，断点已修复
  • 每张业务表带 id/hospital_id/created_at/updated_at，软删除用 deleted_at
  • demo 系统可演示，P0 核心链路全通，已拿给业务方/客户验证过方向
  • 完整工作台 P0+P1 功能开发完毕
  • 每个页面挂载的智能体已配置，准确率 ≥90%
  • 平台标准 skill 优先使用，行业定制 skill 按设计文档开发
  • 返回格式合规：列表 {items,total}、单对象裸返回，业务查询带 hospital_id
  • 异常处理覆盖五类（输入/输出/权限/并发/异常），边界条件全覆盖
  • 智能体调用有超时处理，不卡死页面
  • 过 ruff（后端）、lint（前端）、redline-guard 门禁
  • 部署文档完整，按文档能独立部署；源代码无硬编码密钥
  • 三件套自洽：功能清单 ↔ ER 模型 ↔ 工作台代码 闭环

附：一页纸执行顺序

  1. 验上游 → 检查功能清单+智能体矩阵+真实数据，缺一打回
  2. 建模型 → ER 建模+数据演练，跑不通不开发
  3. 做 demo → P0 功能+核心页面，先出可演示版本
  4. 验方向 → demo 拿去给业务方看，方向不对早调
  5. 补完整 → P0+P1 全做完，异常处理+权限+部署
  6. 写文档 → 部署文档+源代码交付
  7. 过终检 → 交付前终检清单全过，进入阶段五

记住：ER 建模和数据演练最容易被跳过——直接让 AI 写代码看着快，但数据跑不通的代码写得再漂亮也是废代码。这两步做扎实了，工作台才敢放到客户环境里跑。智能体的设计归阶段三、工作台的实现归阶段四，职责不混。
