# 产品介绍制作

以用户给定的四份成品为真实 Word 模板，产出可编辑的客户宣发产品介绍。先确认内容，再用模板填充；默认交付 `<产品名>-产品介绍.docx`。

## 已确认的结构与版式

这四份成品的第一张页面直接开始介绍产品，**没有独立封面**。依次为：

1. 产品名称——居中蓝色标题。
2. 一段产品定位——为谁服务、由哪些能力/智能体组成、做什么、带来什么业务价值。
3. **适用客户群体**——一段说明实际使用部门或机构。
4. **医院需求痛点与现状**——通常 4～5 段，每段先点问题，再说明当前工作与后果。
5. **核心能力与价值**——通常 3～4 段，按能力或子智能体展开，衔接业务问题。
6. **案例（有资料时）**——根据模板使用行内客户案例、独立案例配图或实施前后指标表。
7. **部署方式**——列表说明本产品已确认的模式和条件。

标题编号由原 Word 样式自动生成，不能仅凭提取的文字看不到数字就删除编号，也不要在文本里再写一套“一、二、三”。正文默认沿用 12pt 仿宋_GB2312、Times New Roman、1.5 倍行距、首行缩进两字符；详细实测参数见 `references/template-map.md`。

直接复用 `templates/` 中的 DOCX 包及段落原型，保留页眉 Logo、实际分节引用、样式、编号与版式。不要从空白 Document 重画。不要套用白皮书的大封面或操作手册的截图步骤章。用户本次明确的新要求优先。

## 四种成品模板

| 模板 ID | 成品来源 | 适用情况 |
|---|---|---|
| `operations` | 运营决策智能体-产品介绍.docx | 常规简版，无案例、无正文图片 |
| `hr` | 医院人事管理智能体-产品介绍.docx | 多案例，每个案例可配真实界面图 |
| `quality-risk` | 医疗质量与安全风险预警智能体-产品介绍.docx | 能力后衔接一段完整客户业务故事，无独立案例标题 |
| `perioperative` | 围术期决策智能体-产品介绍.docx | 独立应用案例与“指标／实施前／实施后”表 |

用户说“就按某一份”时选该模板。未指定时，按现有内容最接近的一份选择，不为了使用所有模板而补造案例或数据。

## 工作流程

### 1. 看资料，确定产品定义

阅读本次产品说明、已确认文案和成品。需要验证具体功能时再读 Demo 或线上页面。先读 `references/writing-guide.md`，选模板时读 `references/template-map.md`。

在工作区建立 `analysis/<产品名>产品介绍/`，保存产品内容源、引用依据、原图和最终图。用户原稿保持不变。

使用客户确认的产品定义组织内容。Demo 只显示一部分功能时，不擅自把产品缩减为当前演示页面；明确冲突记在工作底稿并做针对性确认。不要在宣发正文里反复插入“前端模拟、未看到后端、未验证”等开发审计话术。

同时不要新造功能、客户案例、数字或落地结论。用“辅助、支持、供业务人员核对”准确表达产品角色，不把实际业务团队完成的决定写成 AI 自动完成。

### 2. 先写一段产品定位

基本句式：

> `[产品名]，是[部门/角色]的[业务助手]：汇聚/包括[核心模块]，围绕[真实场景]完成[业务动作]，帮助[受益人]获得[结果]。`

功能型产品可采用运营决策成品的写法；多智能体产品采用人事、风险预警或围术期成品的写法。保留产品与子智能体的正确名称、分工和承接关系。不要把定位段写成长串技术栈。

### 3. 写清客户、痛点、能力与价值

- 客户要具体到运营部、人力资源部、医务部、外科、麻醉科、管理层等真实使用对象。
- 痛点先写可感知问题，如“报告靠人工拼”“风险提醒难落实”，再写谁在什么场景下怎么工作、哪一步困难、造成什么后果。
- 能力写为“名称：处理什么信息 → 做什么动作 → 输出什么 → 业务人员如何使用”。讲清业务价值，不停留在“智能化、闭环、赋能、降本增效”等概念。
- 把痛点与能力对应起来，但不强求段数完全相等。一个能力解决几个问题时可以自然合并。
- 沿用成品自然段风格；不自动拆成十多个编号章节，不增加目录、产品白皮书副标题、版本封面、按钮操作流程或泛化行业综述。
- 保持简短介绍的篇幅；内容多少由真实业务决定，不能为了固定页数删重要内容或灌水。

### 4. 有依据地写案例与部署

案例写“原来的工作与问题 → 智能体做了什么 → 业务人员怎样处理 → 最后发生什么变化”。资料不含真实结果时，改成明确的应用场景或省略案例，不将虚构情境标为“客户案例”。

成效表必须有同口径的前后数据，记录指标定义、统计期间和资料来源。不得复用另一份成品中的 43 台手术、4 位患者、28%、25%→85% 等数字作为新产品效果。原文不同基线存在疑问时，在底稿中提出，不暗自统一数字。

部署方式按本产品资料填写。订阅、私有化、混合部署不能机械全选；计算、模型、应用及数据的位置分别写准。参考运营决策成品中出现“教育算力底座”，是应核对的领域表述，不是所有医疗产品的固定文案；别在新产品里照抄这个疑点。

### 5. 在真实模板中生成

读 `references/content-format.md`。先导出最接近的成品为可编辑 JSON，再**完整替换与当前产品有关的内容及配图**：

```bash
<python> <skill目录>/scripts/product_intro.py export --template operations --output-dir <工作目录>
<python> <skill目录>/scripts/product_intro.py build <工作目录>/product.json --output-dir <交付目录>
<python> <skill目录>/scripts/product_intro.py verify <工作目录>/product.json <交付目录>/<产品名>-产品介绍.docx
```

`export` 导出的文本是来源成品，供理解结构与同产品修订。跨产品创作不能只改标题。新文档的案例图必须来自相应产品；不把包内未引用的旧图片自动加进正文。

脚本只修改必要的正文与新图片关系，复制原样式和实际页眉引用，保持图注在图上方、表格表头等成品细节。默认拒绝覆盖已有输出。批量制作时每个产品分别核对完整内容；无需重新设计公共版式。

依赖安装使用已有虚拟环境，缺少时安装 `requirements.txt`。Skill 不依赖原附件目录，也不调用白皮书或操作手册脚本。

### 6. 核对并交付

- 核对开头没有新增封面，内容顺序和所选成品一致，标题自动编号没有重复。
- 核对患者/医生/管理者的工作责任、子智能体名称与实际资料一致。
- 同时检查正文、图注、图片、文档属性，防止旧产品名、旧截图和旧案例遗漏。
- 检查页眉 Logo、字体、缩进、表格、图片比例与原稿一致；图片关系完整，Word 内容可编辑。
- 脚本可验证样式与引用保留、内容完整性和包结构；实际换行分页需在 Word/WPS/LibreOffice 中渲染或目视核对。不得把结构检查说成视觉验收。
- 默认交付 Word；用户需要 PDF 时从最终 Word 转换并复查，不能只改扩展名。
- 最后给出文件链接。根据实际完成的检查说明成果；待核实细节只在影响本次使用时简要指出。

## 修订与原稿忠实度

用户批评不一致时，先对照其原文件的标题、正文顺序、页眉/封面、编号与图文布局，定位差异后修改内容源。保留已确认的商业表达，不把“忠实原稿”理解成只复制字体参数。

这四份文档是用户授权的模板和学习样本，仅用于本用户的制作需求。对外输出的是指定产品介绍，不能将来源文档中的其他客户数据或无关资源误展示为新产品资料。
