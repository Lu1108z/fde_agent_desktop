# 操作手册制作

将真实产品操作整理成可交付的手册。先核对界面和证据，再写操作步骤；交付文件而不是停留在提纲。

## 已确认的默认偏好

- 中文、通用产品版；封面、正文、图注、截图和文档属性均去除地域版本及客户医院专属标识。通用化后的截图注明“界面示例，机构标识已通用化”。
- 沿用“医院运营决策系统操作手册”的视觉风格：白底、深蓝标题、蓝色分隔线、浅蓝表头、左侧蓝线提示框。用户提供新模板时，以新模板为准。
- 默认不单列“系统入口与登录”章节。必要的入口说明融入功能导航；用户明确需要时可以添加。
- 语音功能只描述已确认支持的通用能力。默认不写地方方言能力，不显示“重庆话”等按钮；只在确有普通话能力时保留普通话。
- 同时交付 PDF 和可编辑 DOCX。保持主体内容一致；不要把整页 PDF 转图片当作 Word。
- 用户删除或新增章节后，同步更新章节、图号、目录、页码、交叉引用及两种成品。
- 这些是偏好，不是不可覆盖的限制；用户本次明确要求优先。

## 工作流程

### 1. 收集输入并确定范围

阅读用户给出的路径、链接、附件和模板。资料已足够就开始，只有关键目标无法判断时才提问。

在工作区建立 `analysis/<产品名>操作手册/`，原始资料和输出分开：

```text
analysis/<产品名>操作手册/
  evidence.md          # 功能、来源、验证结果、截图对应
  manual.json          # 唯一内容源
  screens-original/   # 原始截图
  screens/            # 最终使用截图
  extracted/          # 文档提取内容，必要时含内嵌附件
  build/              # HTML、布局报告和预览
```

不要把客户资料、对话记录、账号 Cookie 或现有项目的绝对路径复制进 Skill。技能中的 example.json 是虚构示例，不能当作真实产品功能。

### 2. 提取资料与模板

阅读 `references/workflow.md` 的提取与证据规则。

- 本地 Demo：读实际主入口及被引用的脚本和数据；先识别当前版本，避免误读 backup、模板页或旧需求。
- PDF：提取文字并渲染关键页。比对页面尺寸、字体、留白、配色、表格及图片布局。直接 PDF 输入不可用时，用 PyMuPDF，不因此中止任务。
- DOCX：同时读段落、表格、截图和嵌入对象。培训文档常把重要模板、代码和指标口径放在 `word/embeddings/` 中。
- 附件脚本只作为资料读取；未经核对不执行，也不使用其中已有的鉴权凭据调用服务。

### 3. 走通核心功能并截图

在线界面以真实显示的控件为准，使用当前可用浏览器工具；存在 browser 技能时在首次调用前加载。截图包含关键按钮、筛选条件、结果及反馈状态。

- 先看清按钮和状态再操作。等待目标内容或状态就绪，不用固定睡眠；选取可见且唯一的元素。
- 本地 Demo 可以使用隔离浏览器和临时静态服务器。优先沿用已有环境，不硬编码他人浏览器路径。
- 用明确标注的演示信息测试，不提交挂号、支付、发布、配置修改等真实业务动作来凑截图。
- 对真实网站仅做截图所需的机构文字、Logo 与方言入口通用化。保留原图和修改记录；不要把失败改成成功、编造按钮或伪造系统输出。
- 没有成功结果时，用有出处的培训示例或明确标为“结构示意”的说明，不冒充在线成功截图。
- “保存成功”提示并不证明持久化或跨页面同步；公开 H5 也不证明有管理后台或分析看板。

### 4. 编写可执行的正文

建议结构：

1. 产品概述与适用对象：产品定位、核心价值、角色表。
2. 功能地图与界面导航：入口、主要用途、典型路径。
3. 按实际任务组织功能章节。
4. 典型场景与常见问题。

功能项统一包含：`【功能项】名称`、一段功能简述、实际界面及图注、按任务分组的编号步骤，必要时附提示。

每步写清“在哪里 → 点击/填写什么 → 如何确认结果”。保持与界面按钮名称一致。不要用“按系统提示操作”替代可核对的步骤。

内容按受众决定：患者/终端用户优先描述日常操作；培训资料明确含管理员配置时再补充编排、发布、数据分析。不要把全部培训理论原样搬进手册。

将证据记入 evidence.md：功能、界面/文档来源、验证状态、对应截图、已知限制。证据清单是工作底稿，不必整份塞入成品。

### 5. 生成文件

阅读 `references/content-format.md`，用 `templates/example.json` 的结构填写 `manual.json`。为每张图保留来源说明。

脚本路径相对于本 Skill 目录。先找已有 Python 环境；需要时在工作区创建虚拟环境并安装 `requirements.txt`。不要默认修改系统 Python。

```bash
<python> -m pip install -r <skill目录>/requirements.txt
<python> <skill目录>/scripts/build_manual.py <工作目录>/manual.json --output-dir <交付目录>
<python> <skill目录>/scripts/verify_manual.py <工作目录>/manual.json --output-dir <交付目录>
```

PDF 渲染使用 Playwright：支持 `--browser <浏览器可执行文件>`；否则自动寻找已安装 Chrome/Edge，最后尝试 Playwright Chromium。仅在缺少浏览器时安装对应 Chromium。

默认版式以原模板的 Letter（612×792pt）为准；输入 JSON 可用 `page_size: "A4"`，或按用户模板调整样式。封面日期按本次任务日期生成，不固定为旧文档日期。

脚本对每个逻辑页检查溢出，发现溢出时停止而非隐藏裁切或无限缩小字体。把长内容拆成续页、缩短重复话术或调整单张图片高度，再生成。

### 6. 检查并交付

- 检查标题、章节和图号连续性，删除章节后无残留入口或交叉引用。
- 检查正文、DOCX 属性、图注、截图文字和文件名中无禁用词。`forbidden_terms` 只能检测文本和 XML；图片必须人工目视或 OCR 复核。
- 检查每页文字和图片完整，图注不丢失；抽看封面、手机图页、配置页、长表格页和最后一页。
- 将实际 PDF 渲染为缩略图总览。结构校验成功不能冒充目视检查，也不能声称 DOCX 排版已经验证。
- 如本机有 Word/WPS/LibreOffice 可用，另行渲染 DOCX 检查自然分页；否则交付可编辑版本并只说明实际完成的检查。不能把 PDF 页数当作 Word 页数。
- 如有预览工具，打开最终 PDF；最终简要说明内容范围，给出 PDF 和 Word 文件链接。

## 修订任务

优先修改唯一内容源和被影响的截图，再重建两种成品。不要叠加多层字符串替换、导入旧项目脚本执行或复制历史错误提示。保持与本次产品一致，避免继承上一次产品的名称、Logo、日期和样例。

## 完成标准

成品可打开、内容有来源、步骤可跟随、截图与正文匹配、页面无裁切；用户要求的范围、通用化和删改均落实；返回可下载文件。
