# FDE 阶段一：资料解析

## 原则
- **已经知道**只放资料原文明确支持的事实，每条写出来源文件相对路径。
- **可能需要了解**是 AI 基于行业经验推断的潜在问题，必须写推断依据，不得冒充客户事实。
- **尚未确认**是访谈中需要客户回答的问题，标注所属维度和建议责任人。
- 资料少时照常输出，维度标为 missing 或 partial，不阻止后续工作。

## 六个调研维度
| id | 维度 | 判断"complete"的最低条件 |
|---|---|---|
| scenario | 业务场景 | 明确使用场景、覆盖部门与业务范围 |
| roles | 用户角色 | 明确使用者、决策者及其诉求 |
| process | 现有流程 | 能描述关键环节、输入输出与交接点 |
| data | 数据系统 | 明确涉及系统、数据来源与可获取性 |
| pain | 核心痛点 | 有客户陈述的具体问题及影响 |
| value | 价值目标 | 有可衡量的期望效果 |

状态取值：missing（无信息）、partial（有零散信息）、review（有信息但存在矛盾或仅为推断）、complete（满足上表条件）。

## 写法要求（结论要让人一眼看懂）
- 每个维度的 summary 写成完整句：「已知 … ；尚不清楚 …」。不要用斜杠堆名词。
  - 差：`HIS/HRP/考勤/OA/Excel，CDR 与考勤接入待确认`
  - 好：`已知排班在 Excel、考勤用独立考勤机、人员档案在 HRP；尚不清楚考勤数据能否导出、集成平台是否已有 CDR`
- 每个维度写 reason，说明为什么判这个状态（例如"系统清单明确，但接入方式均未确认 → review"）。
- 资料里写了的就进 known，并写出来源路径；只有资料没说的才进 unconfirmed。不要把能从资料读出的内容全部改写成问题。
- known / possible / unconfirmed 每条都标 dimension，便于按维度查看。
- 待确认问题要具体可问：写清问谁、问什么，例如"信息科：考勤机厂商是谁，能否按日导出打卡明细"，而不是"考勤接入待确认"。

## 输出
按调用方给定路径写 JSON，结构以调用提示为准。summary 用一两句话说明资料覆盖情况和最大缺口。
