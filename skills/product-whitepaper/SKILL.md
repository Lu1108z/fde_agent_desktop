# 产品白皮书制作

## 最高优先级：忠实沿用原稿（用户纠正后的规则）

用户要求的是原稿模板复用，不是“参考风格后重新设计”。默认必须使用 `templates/reference.docx`（用户提供的原始白皮书），保留真实封面、Logo、图片对象、页眉页脚、分节、字体及段落格式。不得用空白 Document 重新画封面，不添加“产品白皮书·通用版”副标题，不手动拆封面产品名。

正文顺序固定为：产品名称与定位段 → 适用客户群体 → 医院需求痛点与现状（患者侧、医院侧）→ 核心能力与价值（体检报告智能体：把报告讲清楚；健康管理智能体：让健康有人管）→ 部署方式。迁移到其他产品时替换对应的角色和模块名称，但保留这个组织顺序；未经用户要求，不合并客户与痛点，不改为功能菜单式六章，不添加一、二、三编号。

同产品修订以用户白皮书为产品定义来源。不能因为 Demo 没有展示全部能力，就擅自删除原稿的健康管理、导诊入组或两种部署模式；明确存在冲突时向用户指出冲突，不能自行改写成 Demo 技术审计报告。Demo 实现限制保留在工作底稿，不把反复的“模拟、未验证、无后端”插入营销正文。

默认生成入口改为 `scripts/build_from_template.py`。先运行 `--inspect` 查看段落索引，再准备明确的逐段替换清单；内容替换不破坏原有绘图和排版对象。封面、图文关系和标题顺序必须与原稿对照。旧 `build_whitepaper.py` 仅允许用户明确要求全新设计时加 `--free-layout` 使用，不再作为默认路径。

跨产品替换还必须处理旧正文及业务截图，不能只换产品标题。脚本不自动猜测修改内容，也不自动删除原有截图；需要换图或增减段落时，基于模板的对应 XML 节点操作，并核对关系与分页。不能把结构检查等同于 Word 视觉验收。

将已核对的产品能力转化为面向客户决策者的业务说明，交付可编辑的成品文档。默认采用用户提供的《体检报告解读智能体白皮书》所体现的简洁结构和黑白排版。用户指定新模板时以新要求为准。

## 默认偏好

- 中文通用产品版，除非用户指定客户版，否则不保留地域版本和客户医院标识。
- 默认交付 DOCX。用户需要 PDF 时再生成并检查；不要只修改扩展名，也不要将整页图片充当可编辑文档。
- 封面含产品名、编制团队与英文团队标识。参考文档为 `360-FDE`、`MEDICAL TEAM`；仅适用于同一授权品牌与医疗业务，其他行业必须调整，不能自动宣称为其编制。
- 正文采用“定位 → 客户 → 痛点 → 能力与价值 → 部署方式”的叙事。登录、点击步骤和按钮操作放在操作手册中，不作为白皮书主体。
- 默认不单独添加目录、修订记录、冗长行业综述、技术名词百科。根据产品复杂度决定篇幅，不为凑页数扩写。
- 引用当前实际支持的通用功能；不继承上一个产品的名称、方言能力、医院信息或部署承诺。

## 工作步骤

### 1. 理解参考文档与业务资料

读取本次参考文档的段落、标题层级、图片、表格、页面大小、字体和封面排版。默认视觉参数见 `references/style-and-narrative.md`。

建立工作目录 `analysis/<产品名>白皮书/`，保存原始截图、最终配图、证据清单和唯一内容源 `whitepaper.json`。不要修改原始附件。

资料优先级：用户明确确认的当前产品定义、当前演示界面及实现、产品说明和培训资料、历史参考内容。对冲突之处记录来源和状态，不简单用“看起来更完整”的版本覆盖实际功能。

### 2. 建立事实与价值对应表

先记录 `客户角色 | 业务问题 | 产品能力 | 输入/处理/输出 | 客户价值 | 证据与实现状态`。

- 区分“已验证”“文档说明”“演示”“规划”能力。没有证据的规划不能写成已交付功能。
- 产品价值写清改善哪个环节、由谁承接后续工作。没有数据时使用定性表述，不编造效率提升、转化率、准确率或覆盖规模。
- 涉及不同智能体的协作，明确职责、交接信息和输出，避免只列智能体名称。
- 医疗场景：报告解释不等于诊断；问答不等于真人问诊；筛查不等于确诊；分诊不等于完成挂号；推荐不等于已完成服务转化。
- 人群分层、风险筛查、慢病管理、导诊入组等必须有当前产品资料支持。参考白皮书中的这些能力不能自动套用到新产品。
- 部署模式需核对计算、应用和数据所在位置、医院所需资源与对接方式。不要无依据承诺“数据不外传”“完全私有化”“无需开发”。

### 3. 撰写正文

参照 `references/style-and-narrative.md` 逐段组织，优先使用具体、可验证的业务表达。

1. **产品定位**：一段说明服务谁、从什么业务对象切入、做什么、输出什么、为何有用。将最关键差异点写在段落前部。
2. **适用客户群体**：点明机构类型、组织部门、适用业务条件；不扩大到没有资料支持的行业。
3. **需求痛点与现状**：按患者/医院、员工/管理者等真实角色区分。每个痛点包含短标题与具体业务后果。
4. **核心能力与价值**：按产品模块或智能体职责分组。每组先写一句价值定位，再写若干“能力名——业务动作、输出及价值”。能力之间保持清晰边界。
5. **代表性配图**：使用真实界面、已有合规示意或标明来源的架构图，图注直接解释图展示的内容。
6. **部署方式**：只列已确认可提供的模式和前提；信息不足时在工作底稿记录待确认，不在成品中补造销售承诺。

必要时可增补典型应用场景、业务流程与成效衡量口径，但不要机械扩成固定十章。

### 4. 处理配图

- 保留原图，另存通用化配图。裁剪无关留白，保留关键结果和识别上下文。
- 通用版去除机构专属名称、Logo 和地域标识，图注说明机构标识已通用化。
- 不修改失败为成功，不编造不存在的能力，不将训练材料截图冒充当前线上实测。
- 手机页面可并列展示；保持比例，保证在 Word 页面内可读。图与图注相邻，必要时另页展示。
- 默认保留参考文档的“图一、图二”图注风格，脚本自动编号。

### 5. 生成并检查

读取 `references/content-format.md`，参照 `templates/example.json` 创建内容源。使用现有 Python 虚拟环境；缺依赖时安装本技能 `requirements.txt`。

```bash
<python> <skill目录>/scripts/build_from_template.py --inspect
<python> <skill目录>/scripts/build_from_template.py --edits <工作目录>/replacements.json --output <交付目录>/<文件名>.docx
```

默认脚本直接保留原模板包内对象，仅修改明确指定的段落文字；完整排版资产已包含在 Skill 中，不依赖下载目录中的原文件。

- 核对能力与证据、痛点与能力是否对应；正文没有未替换的示例、占位数字或旧产品名称。
- 核对封面品牌、正文与图注的机构标识、图像清晰度、编号和部署说明。
- 检查文字字体、页面尺寸、图片边界和文档结构。结构检查不能证明 Word 实际分页正常。
- 如有 Word/WPS/LibreOffice，渲染 DOCX 复核封面、分页、配图与最后一页；如无可用转换器，明确只完成内容与结构校验，不宣称做过视觉验收。
- 用户要求 PDF 时优先从最终 DOCX 转换以保持一致。转换不可用时可生成独立 PDF，但必须检查两种格式的内容一致性并说明分页可能不同。

### 6. 交付与修订

给出可点击的文件链接，简要说明涵盖的内容和必要的未验证项。用户修改定位、删模块或换图时，更新唯一内容源并重新生成，保留用户手工修改的成品。

## 禁止的捷径

- 用操作步骤代替产品价值说明。
- 无证据把产品发展愿景当作现有功能。
- 把“咨询量”写成“就诊转化”，把“有按钮”写成“已完成业务闭环”。
- 使用原参考文档中的医院、患者资料、截图、品牌或数字作为所有产品的默认事实。
- 要求用户批准尚未形成的空计划；资料足够时先完成可审阅成品。
